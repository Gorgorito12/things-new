# Address map of the original DLL

Every site upstream AoE3UnHardcoded (v1.10, `reference/AoE3UnHardcoded/DLL`) patches in `age3y.exe`.
Target: stock Steam build `b1a1dab7…11d9d` (see [binaries.md](binaries.md)). Upstream checks only the
file size; the rows below record what was verified against this build on 2026-10-28.

## Conventions

- **Type** (semantics follow `PatchCodeCave`, `Utilities.cpp:50-217`)
  - `replace`: a 5-byte `jmp` at Site into DLL code that ends with a `jmp` to End. Only [Site, Site+5) is
    overwritten; [Site+5, End) stays intact but is skipped on this path.
  - `detour`: Site == End. Instructions starting at Site are relocated to a trampoline until ≥5 bytes
    are covered ("stolen"), and the hook runs first.
  - `redirect`: Site gets a `jmp` to a far End inside the game.
  - `case`: a 4-byte jump-table slot is overwritten.
  - `write32` / `bytes`: a raw data patch.
- **Status**: `unverified` → `confirmed` or `mismatch`. `confirmed` means:
  - Site (and End, where the cave falls through to it) is an instruction boundary in the stock exe;
  - the instructions there are the ones the upstream cave re-executes or replaces.
  - It says nothing about whether the cave's own logic is correct; cave defects are listed separately below.
- **Evidence**
  - `E1` = `ev_8c926efbad761e059e1481527b402bf332733a18a1facd63ab8ffd8bf7a27d4e`: REA `batch_decompile` of every site; gives the containing procedure.
  - `E1` was re-run as part of `E3` (`ev_c2186c76…`, see [engine-symbols.md](engine-symbols.md)); every site's containing procedure was identical.
  - `E2` = `ev_a75f4dbc0f32a99229e13cffcbc07942a0fdef1d56c4ec8119c1d93049ac7287`: REA `procedure_assembly` of FUN_00603ab7. Its record was not saved to disk; the same listing is in `cs` (`sites.txt`).
  - `cs` = capstone 5.0.6 disassembly of the file bytes, with two boundary checks:
    - a linear decode from the Ghidra entry, where the site lies in the entry's contiguous chunk;
    - decodes from Site−1…Site−48, which must land on Site.
  - Scripts and outputs are local evidence in `rea/evidence/age3y-b1a1dab7/` (not in the repository). The method, with a runnable example, is in [developer-guide.md](developer-guide.md#byte-level-checks-with-capstone).
- **Function**: the containing procedure from `E1`. "—" means the address lies in no Ghidra function (13 sites); those addresses resolve only through REA's file-offset fallback, so `E1`'s pseudocode for them is unrelated and must be ignored.
- **Source refs** are `file:line` in `reference/AoE3UnHardcoded/DLL`. The cfg key → patch dispatch is in `UHC.cpp:158-329` (parse) and `UHC.cpp:416-482` (apply).
- **Byte notation:** `NNh` = hex and `B` = bytes (`5 B` = 5 bytes). `[x]` = memory at x; `[C66234h]` is the game object pointer.

**hcShipmentPointFallback, how it works.**
- The original exit is the "no valid gather unit" path of FUN_004C6B9E: `pop ebp/edi/esi; xor eax,eax`, continuing at 0x669E33.
- The hook searches each configured proto with the stock unit query (0x453618 / 0x45356D / 0x4532B4 / 0x453484 / 0x453A36) and applies the same three checks as the stock blocks (verified copy: 0x6698B4..0x669963).
- The keyword `FirstTC` (entry -2, tested before any query) takes the player's first town center `[player+4F0h]` (player 0x44CB21, unit 0x44CC6D), requires `[[unit+44h]]` = the player ID, and calls the stock stored-point check 0x85302C (site `GatherPointValid`). The helper writes no game state.
- On success it jumps to the stock store-and-return path, 0x4C6CB2.
- Proto names resolve on first use through 0x5A2346; `FirstTC` maps to -2 before any lookup.
- Multiplayer is unverified. `FirstTC` was confirmed in game with `civFirstTC` (2026-10-29): the helper returned a Market that was the player's first town center, 0x4C6CB2 stored its ID in `[hc+18Ch]`, and a card's crates landed there.

**Stock behavior** (dynamic trace with `tools/re/trace_writes.py`; the original log, `hwbp-log.txt`, is local evidence): deleting the TC clears the point (0x6697F5, on FUN_004C6B9E's store = 1 path). FUN_004C6B9E then moves it, but only to one of 10 types: TownCenter, Outpost, FortFrontier, WarHut, Blockhouse, NoblesHut, AbstractAgraFort, AbstractDaimyo, ypCastle, ypVillage (`docs/engine-symbols.md`, "Home city gather point").

**healNonIdle, how the sites were found.**
- **First version: tick only.** It patched only the heal tick. In game, surgeons still ignored a fighting explorer, and the tick hook was never reached.
- **Dynamic trace** (`tools/re/trace_exec.py`; the original log, `hwbp3-log.txt`, is local evidence): the action is started by the automatic search FUN_009CD865, which only takes idle targets (0x44F1A7).
- **Not this predicate.** FUN_004C6CD7 (codes 0x41/0x42) also tests "fighting", but the trace never reached it while healing.

- **Still unverified:** whether a direct order (right-click) on a fighting unit goes through any other filter, and the unmarked control (the British Explorer as healer). Multiplayer is also unverified.

**damageOverTime, how the sites were found.**
- **The stock poison is a dead end.** TakeDamage tests the Poison flag and posts event 20h to the attacker, whose attack action passes `(damage × −0.1, 3.0)` to 0xB1BE43, an empty `mov al,1; ret 8` ([engine-symbols.md](engine-symbols.md), "Damage and poison"). Filling that stub was not chosen: the event only fires while the attacker's current action is still the one that hit (a ranged attacker may have retargeted when its projectile lands), and the stub's arguments are fixed (−0.1 × damage for 3 s).
- **Hit trigger: TakeDamage's entry.** Every damage source goes through it (18 call sites), and it returns the damage dealt. Melee and instant ranged hits were confirmed in game, and on 2026-10-29 flying arrows, grenades and cannon balls and area damage too: the projectile's hit reaches TakeDamage with the launcher's proto ID and action, and an area attack calls it once per unit (which caller is the splash path was not traced). The trace that found it: a hardware write breakpoint on the explorer's HP (`tools/re/trace_writes.py … unit:Explorer+0x64`) stopped in FUN_004823A3 called from 0x49B822.
- **Tick: the world update's entry.** FUN_00481A57 advances the game time and is the only world step; the wrapper ticks after it returns, for the game world only.
- **Data: the parser's unknown-tag fall-through,** the only point every unknown `<ProtoAction>` child reaches (handlers return to 0x5FA126).
- **Confirmed in game (2026-10-28):** Gaia lions, macaques and wandering horsemen hit by the explorer lost 20 HP per second (14 against the horsemen's ranged armor), renewed by each hit, and several died from the poison alone. Multiplayer is unverified.

**The WoL features (2026-10-29), how the sites were found.** These are the Tier 2 features and, from Tier 1 and Tier 3, `startingTC`, `civFirstTC`, `transformInventory`, `noTrainNearEnemyTC`, `overhealHitpointBars`, `showGatherRate` and `buildingWorkRateAuras`. All were found statically with capstone on the stock exe (`cs`), in a scoping pass per request, each checked by a second, adversarial pass; the scoping scripts were not exported to `rea/evidence`. The engine details are in [engine-symbols.md](engine-symbols.md); every site range is in `tools/gen_sites.py`.
- **liveBuildingWorkRate.** A sweep for writers of the per-building copy `[[unit+68h]+28h]` found one apart from its init and save/load: 0x6A2095, in the completion routine. Its only readers are the getter 0x9BFE3A and the save. The getter has four direct callers and no other reference. Not chosen: refreshing every existing unit after the tech effect case 0x5E, which misses the other writers of `[proto+D0h]`. The smallest alternative, `74 04` → `EB 04` at 0x9BFE38, gives the same behavior without a log. TrainPoints (2026-10-30): the writers of the Train action's `+64h` in its code (0x9E9F00..0x9EC300) are the enqueue (0x9EB1B0, 0x9EB1DB), the init (0x9EB47C) and the load (0x9EC067 / 0x9EC131); its readers the fraction 0x9EA1FA and the save 0x9EA539. The Maintain cycle's `+6Ch`: the cycle start (0x9E2A13, 0x9E2A3F) and the fraction 0x9E27E4. Not chosen: redirecting the two calls 0x9EA4B3 / 0x6AB264 (0x6AB264 is inside maintainWaitForPop's verified `MaintainCycleDone`), and refreshing every queued action from the tech effect (it misses triggers and other writers of `[proto+6Ch]`).
- **techPrereqRecheck.** The prerequisite list evaluator FUN_005094B4 has one caller, FUN_005094D8, which has one caller, the pass at 0x5096D4, which has one entry, the `jne` at 0x491A1C. 0x491A18 is reached by every tree update after the DynamicCost loop; no branch targets its inner bytes.
- **maintainWaitForPop.** The bug is at 0x6AB28A: after `call 9E2DEFh` the update tests only the SingleUse flag; the spawn's outcome is never read. The hook holds the cycle at full (not paused while capped), so the building keeps one finished unit ready. A variant after the call, reading the number of units created (`[0xDD0098]`), would also hold build-limit and placement failures, which could block a building forever; it was not chosen.
- **snareOnlyHitUnit.** There is no "snare" string: the snare is the tactics tag `<TargetSpeedBoost>`, read only by FUN_0048FA07. The group recompute FUN_004FD289 is the spread. The second pass found the straggler rule (group bit 7): replacing the group minimum alone would still slow the group to 0.83×. It also added flag 15h to the snare signature, since WoL's exclusive speed auras share flag 16h.
- **transformUpdatesLOS.** FUN_009C754C is the only function that changes a live unit into another proto in place. In game, the trigger effect "Change Unit Type" never reached the hook: it takes another path, and the unit (same ID) already had the new proto's LOS.
- **gaiaSocketsOnly.** The only owner test on the placement paths is the UI snap (0xA0383B); PLACE never reads the owner. In game the stock UI already refused a player's socket; the order path that bypasses it was not driven.
- **startingTC.** `StartingTC` is not a string anywhere (exe, WoL DLLs, WoL data); the exe's own "starting TC" is the placement rules' `FirstTC` (string 0xBCAE7C), `[player+4F0h]`. A scan of every `[reg+4F0h]` operand found its only writers: the ctor (-1), the init, the save/load and addUnit's store 0x67ABD4, reached only from the TownCenter compare 0x506B3B, which runs only while the field is negative (0x49880A). Nothing clears it when the unit dies. The 25 code readers of the TownCenter ID `[db+5E08h]` were classified one by one (scoping of request #3); only 0x506B3B feeds FirstTC, so the other `TownCenter` checks (AI, age-up picker, start camera, …) are not covered.
- **civFirstTC.** Built to the design of WoL's developer Mandos: a `<firstTC>` tag in `civs.xml`, a substitution where map code places `TownCenter`, none in a Nomad start. The civs.xml parser FUN_0052A590 sends every child tag it does not know to one path (0x52BB07), the natural place to read a new tag. Every `rmPlaceObjectDef*` reaches objectDef::place through one call (0x925F4C), so redirecting that call covers every map without touching the scripts; the `Special_StartingUnits` def is left alone, since place rebuilds its items from the civ's `<startingunit>` list. Of the 25 readers of the TownCenter ID, 0x679AC8, which the scoping had filed under `startingResourceDelay`, is the query of the town starting units (FUN_0049039A), and its spawn FUN_007C238E serves only a building where a colony starts. The request flag behind it was found in game: on Mongolia, a Market that was FirstTC, with a colony at it, got no settlers; the request bit `[player+349h]` & 40h is set when a unit with proto flag 136 (`StartingColonyBuilding`) is created (0x6A214A), and the Market got its 6 Settlers once it had that flag.
- **transformInventory.** Static scoping (capstone) found no `+94h` / `+E0h` operand in FUN_009C754C (0x9C754C..0x9C7984) and no inventory write in its callees to depth 3; the only seeding of an inventory is creation's cold chunk 0x67DE0D and the load path 0x9C5596. The owner-change rescale (0x5146E4..0x5147A0) is why the conversion needs no hook once inventories match their proto.
- **noTrainNearEnemyTC.** The Train update FUN_009EA28B makes no proximity query, and the Daimyo / Shogun proto IDs are read only by the command panel (0x6960AA..0x696157). - **overhealHitpointBars.** The max HP getter 0x480408 (45 callers) and the health ratio 0x45F295 (25) are read by simulation code (heal search, transforms, the modifier recompute, AI, triggers), so neither is patched: the hooks replace the calls and loads of the display code only (the floating bar chunk, the selection group, three HP texts, one of them an inlined copy of the getter). ## Known upstream defects (do not reproduce)

Found by reading upstream source (2026-10-27):
- **customSyscalls table overflow.** `customSyscalls` writes past its table: `TABLE_COUNT` is 11 while `Upls` is index 11 (`UHC.h:13,27`, `UHC.inc:58`). It clobbers BasePop/ExtraPop/DeckCardCount (`UHC.cpp:310`).
- **tacticSwitching IDs.** `tacticSwitching` alone never resolves its unit IDs, because UnitCheck only runs for other keys (`UHC.cpp:425` vs `Units.asm:718`).
- **Team-limit dtor.** The team-limit cave skips the BString destructor: it loads `0x4010CA` but never calls it (`Limits.asm:105,141`).
- **Plugin calling convention.** Plugins' `UHCPluginMain` is called as cdecl, though documented as stdcall (`UHC.cpp:385`).
- **Plugin loading.** `LoadLibraryW(fd.cFileName)` loads plugins by bare filename, so directory paths don't resolve.
- **Branch relocation offset.** `PatchCodeCave` reads `lpBuffer+1/+2` instead of `+dwSize` for rel32 branches (`Utilities.cpp:111,125`). That is only correct when the branch is the first stolen instruction. In this build every relocated branch is first (TeamLimit MP, AttackTypeIcons #2), so the bug is latent.
- **Config parser.** It has an operator-precedence bug (`Config.cpp:74`), and a single `/` aborts the parse (`:69-70`).

Found against the stock exe (2026-10-28; static inference, not observed at runtime):
- **AILimit leaves two locals uninitialized.** The replaced range also holds:
  - `mov dword [esp+28h],0` at 0x603B44. It runs after `push 2`, so it clears ESP+24h, the loaded-personality counter used as the array index at 0x5DE154/0x5DE2C1.
  - `mov byte [esp+1Fh],0` at 0x603B4C, which clears ESP+1Bh, the function's return flag (0x603DCD).

  The cave skips both, so they keep stale stack contents. A new implementation must zero them.
- **AsianCivs #3 tests EAX instead of AL.**
  - Stock uses `test al,al` after `call 49A2D8h`; the cave uses `test eax,eax`.
  - The callee returns false with `xor al,al`, which leaves EAX's upper bytes untouched. On the "civ has no entry" path (`or eax,-1` at 0x679D16) EAX becomes 0xFFFFFF00.
  - As a result, the cave takes the true branch for a false result.
- **NativeCivs #4 compares a dword where stock compares a byte.** Stock uses `cmp byte ptr [esp+4],0`; the cave uses `cmp dword ptr [esp+4],0`. Garbage in the upper bytes of the caller's bool argument would select the `[C6FB5Ch]` path.
- **PatchCodeCave relocates garbage when End − Site < 5.** For CivCheck #1 and NativeCivs #4, End lies inside an instruction. `PatchCodeCave` decodes from that mid-instruction byte and copies the result into a trampoline. The trampoline is unreachable, because the cave jumps or returns explicitly, but it is still built. A new implementation should take the real continuation address instead.
- **FameRestriction #2 passes the wrong owner.** In FUN_0081922A, stock passes **EDI** to 0x4539D3 for each cost line (ESI is the UI object there). The upstream cave at 0x81943D reuses the block from #1 and passes **ESI**.
  - Our DLL passes EDI.
  - In the stock functions, #1 already lists resources 2, 1, 0 and 7, and #2 lists 2, 1 and 0.
- **PopLimit misses the negative-extra path.** When `[edx+4F8h] < 0`, stock jumps from 0x679611 to 0x4581FC with ECX = 0. That address lies past the 5 patched bytes, so the stock 200/world/250 clamps still apply. Our DLL also hooks 0x4581FC.
- **PopLimit leaves shared team population alone.** In that mode (`[world+6913h] != 0`, out-of-line at 0x679641), each player is capped at 200 and at world+31Ch. This path is unpatched, both upstream and in our DLL.
- **PopLimit drops two clamps** besides lifting the 50/200 limits:
  - the clamp against `[[[C66234h]+13Ch]+31Ch]`, a world-level value, probably the game-setup pop cap (inference);
  - the final 250 cap.
