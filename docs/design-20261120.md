## #70 Politician UI (`politicianTechCards`)

**What WoL writes.**
- In `techtreey.xml`, inside a politician's `<Tech>`: one `<PoliticianEnablesTech>Name</PoliticianEnablesTech>` per
  tech card, in the order they show (at most 3 per politician; more are ignored with a `dataLint` line). Nothing
  else changes: the `TechStatus obtainable` effects stay as they are, the tag only drives the UI.
- In `uipoliticianEuropeandlg.xml` (the only file the Latin American civs use, see below), inside each
  `PoliticianDlg-PoliticianButton%d`, new gadgets for place n = 0..3 (and 4 if the file gets a fifth place):

  | Gadget | Type | Place 0 at 1024×768 (`size1024`) | What the DLL puts in it |
  |---|---|---|---|
  | `PoliticianDlg-Poli%dFlag` | `gadget`, `texturecoords="0 0 0.75 0.7734375"`, `hidden=""` | `63 194 159 300` (the top of the portrait's rectangle, 96 × 106) | the politician's `portraitfilename` (the flag picture) |
  | `PoliticianDlg-Poli%dTech%dIcon` (k = 0..2) | `button`, `hidden=""`, `foreground=""` | `63 304 103 344`, `63 352 103 392`, `63 400 103 440` (40 × 40) | the tech's `<Icon>` |
  | `PoliticianDlg-Poli%dTech%dName` (k = 0..2) | `formatText`, `textfont="ChatOutline"`, `textfontsize="10"`, `hidden=""` | `107 304 159 344`, … (52 × 40, two lines) | the tech's display name, and its rollover text as the help text |

  Places 1–3 are the same shifted by +236 in x (288, 524, 760, as the stock places). Sizes are a first proposal for
  the 192 × 396 portraits: WoL draws the flag pictures and may move the boxes; the DLL only looks gadgets up by name.
- New flag pictures (the immigrant flag alone) as separate DDTs, named in `politiciandata.xml` as today
  (`portraitfilename`). **(WoL?)** Keep the current combined pictures for politicians without the tag.

**Behaviour.**
- A politician whose tech has at least one `<PoliticianEnablesTech>` (resolved to a tech ID): the stock portrait
  `Poli%dPortrait` is hidden, `Poli%dFlag` shows the same `portraitfilename` texture (with the stock texture
  coordinates 0, 0, 0.75, 0.7734375, which the code sets itself at 0x81A4F3), and each listed tech fills
  `Tech%dIcon` (texture handle `[def+14h]`) and `Tech%dName` (DisplayNameID `[def+8]` through 0x58EA52), with the
  RolloverTextID text (`[def+0Ch]`) as its help text (`[gadget+68h]`, as `minUIStats` does). Unused card gadgets are
  hidden.
- A politician without the tag, a place with no `politiciandata` entry, or a layout without the new gadgets: exactly
  stock (the new gadgets hidden, the portrait shown).
- The name, cost and description of the politician stay stock (`Poli%dName`, `Poli%dCost`, `Poli%dDescription`).

**Sites.**
1. **`AddTechTagHandler` (new shared hook, `src/techtags.*`, `hooks/techtag_hooks.asm`)**, a copy of `prototags.*`:
   a 5-byte `jmp` at the tag tables builder's tail 0x62391D (`pop edi / mov al,1 / pop esi / pop ecx`), which
   registers each added tag in the **definition** table (ESI, `[loader+0C2Ch]`) through 0x59B738, then re-executes
   the four instructions and returns to 0x623922 (`ret`). Handler convention as stock: `bool cdecl(node, def)`, the
   text a BString at `node+14h`, `[def+0]` the tech ID. A tag in that table is also accepted inside `<Prereqs>` and
   `<Effects>` (0x6203A2): say so in the header. Same `kMaxTags` / log line as `prototags`. Add it to CLAUDE.md's
   shared hooks.
2. The handler stores the text (a name: tech IDs of later techs are not known yet). The names are resolved to IDs
   lazily, at the first dialog fill, through 0x600BE1 (`thiscall(db, name)`, −1 if absent; a bad name is logged once).
3. **List start 0x81A3CD** (10 B: `mov edx,[esp+18h] / mov ecx,[ebx+190h]`, re-executed, `jmp 81A3D7h`): hide the new
   gadgets of every place (EBX = the dialog). Needed because a place counted without a fill (0x81A47B → 0x81A823)
   would keep the last opening's gadgets.
4. **Place end 0x81A816** (9 B: `lea ecx,[esp+68h] / call 44C817h`, re-executed, `jmp 81A81Fh`): place n =
   `[ebx+26Ch]`, tech `[ebx+270h+4n]`; if that tech has cards, fill them and swap portrait/flag. Not 0x81A45A:
   `politicianPlacesFix` owns it (before the place is filled), and it verifies 0x81A848 (`PoliticianListEnd`), so
   neither site may be used. The three sites do not overlap theirs; both keys verify their own bytes.
5. Gadgets by name: the dialog's lookup as `politicianplaces.cpp` does (0x40423C / 0x44900A); textures: by path with
   0x638823 (the flag); a tech icon by handle with the `button` vtable `+104h` (0x4C50CF, `(handle, arg2, 0)`,
   `ret 0Ch`). [U] arg2: the tech button passes a value from its frame (0x462453); **test −1 first**, and read the
   stack at 0x462467 in the debugger if the icon does not show.
6. `kFeatures`: after `politicianPlacesFix`; before `dataLint`, whose `kKnownTags` gets `PoliticianEnablesTech`.

**Risks.** Interface only (the dialog is local; nothing reaches the simulation). The fill runs once per opening.
The hover help text was **not** confirmed in this dialog: the whole place is a `button` (`PoliticianButton%d`) above
the cards' parent, and in the 2026-11-20 test the posted hover did not reach the game at all (control included).
If the help text does not show, fall back to putting the rollover in the button's own help text. Asian and Native
dialogs are not touched (different builders); WallMapu uses the Native one (`NativeCivs` in WoL's cfg).

**Tests.** LA civ skirmish (Mexicans or Chileans; profile `hc` with no other game open): Age II dialog with two
politicians tagged, one not; hover each card with the real cursor (no `background`); a fifth politician with
`politicianPlacesFix` on; revolution dialog unchanged; a bad tech name (log). Screenshot of DE's United States /
Mexico age-up dialog: **not taken** (DE was not started; see the report).

## #71 Research while moving (`researchOnTheMove`)

**Today [O].** A research is always a background action (0x9CCB39 adds it with `immediate` 0) and every action in
the list is updated every tick (0x485C44), so the research itself would keep running. What stops the unit is the order
code: before a move it asks the unit (vtable `+8Ch` → 0x487E74 → 0x487DED), which answers "busy" while the action list
holds any Research (0Ch) or Train (0Dh) action (FUN_00487D8B). In game the WiseWoman with a research queued ignored a
move (`uiWorkAtPointer` and a trigger's `Move To Point`): the Move action stayed in state FFh and was replaced by idle
after ~5 s; the research went on and completed. With the queue empty she moved.

**What WoL writes.** `<UnitType>ResearchOnTheMove</UnitType>` on the protos (MapucheWarchief, MapucheWiseWoman, …,
Ethiopian caravans, Rangatira). The type is registered with `RequestAbstractUnitType` as `cantslow.cpp` does.

**Site.** Head of FUN_00487D8B (7 B: `mov eax,[ecx+24h] / test eax,eax / je 487DA5h`). The hook: if the unit
`[mgr+4]` has the type and the busy actions are **only** Research (no Train action, and the current is not a Train),
return 0 (`ret`, plain `thiscall` with no argument); else re-execute and continue at 0x487D92 or 0x487DA5. Hooking the
callee covers its five callers (0x487E1B and 0x672427, 0x898A7B, 0x9AD19C, 0x9CE3BC: [U] what the last four are; check
them in game: at least one may be the right-click "set gather point" of a busy trainer).

**Risks.**
- Determinism: the answer depends on the unit's proto and its actions only (simulation state).
- What other order paths do with the background research: a Stop command, garrisoning (`[unit+6Ch]` ≥ 0 makes the
  base update 0x485B9B skip every action: [I] a garrisoned researcher pauses), a transform, death (the action dies
  with the unit; the refund path is the state 9 cancel). Test each.
- The research rate uses 0x9BFE33(unit) (`liveBuildingWorkRate`, `buildingWorkRateAuras` hook it): unchanged.
- Training units keep the stock rule (a Daimyo still stands still); the request is research only. **(WoL?)** Do they
  want trainers too?

**Tests.** Scenario: `p1=MapucheWiseWoman` with the type, `researchByID` twice (queue), then move, attack-move,
gather (`uiWorkAtPointer` after a posted click), Stop, garrison in a TC; read the action list (`probe.py` in the
scratchpad of this session, or the same reads: `[mgr+14h]` count, `[mgr+1Ch]` array, Research vtable 0xB98078,
`[act+70h]` fraction) and the position. Control with the key off (stands still). The AI's council research.

## #72a Ship-cost tech limit (`shipTechLimit`)

**What WoL writes.** In `civs.xml`, in the WallMapu `<civ>`: `<ShipTechLimit>N</ShipTechLimit>`. Read through
`AddCivTagHandler` (civtags.cpp: `kMaxTags` 8, 6 used, so 2 left; raise it if a third key needs one).

**Rule.** A tech **costs ships** when its cost list (`[status+10h]`, the copy the rollover uses) has the ship resource
(index 6, found once by name through the resource names `[db+180h]`) above zero, and it is not a HomeCity tech
(status bit 18: the cards stay unlimited). The count of a player = his ship-cost techs that are active (bit 1) or being
researched (bit 15). No new state: it comes from the tech statuses, so saved games and every machine agree. With
`count ≥ N`, a ship-cost tech cannot be researched.

**Site.** Head of 0x4C6968 (`push ebp / mov ebp,[esp+8]`, 5 B; no branch into it): the can-research test that the
command panel (0x4620C0, result in BL: the button's state), the AI's research, `researchByID` and **the research
start 0x9E670B** (the command's execution, on every machine) all ask. The hook answers false for a blocked tech, else
runs stock. `ageUpBuildings`' wrapper calls 0x4C6968, so it sees the hook too.
- Cost: the count walks the player's statuses (about 5,000). Cache it per player and per simulation step
  (`[world+F8h]`), and compute it only for a civ with a limit and a tech that costs ships.
- The reason: append a line to the tech's rollover (red, like the stock unmet-requirement lines `\n*  %s` of
  0x4C737C) with a new string, e.g. "Limit of ship techs reached (N)". `researchGrants` already hooks the panel's
  call of the rollover builder (0x4622C5): **make that hook a small shared list** (`AddTechRolloverLine`) instead of a
  second patch at the same call.
- [U] The CommandResearch path (payment 0x9D54CF) asks neither 0x4C6968 nor the HomeCity test: find what creates a
  CommandResearch before relying on the hook alone; else also refuse in an `AddResearchPayer` claim.

**Tests.** WallMapu skirmish with `<ShipTechLimit>2</ShipTechLimit>`: research two council techs (ships from the
home city's shipment trickle), the third button greys with the line; cancel one (the count drops, the button
returns); save and load; the AI's WallMapu.

## #72b HomeCity techs researched from units (`homeCityTechsInUnits`)

**Today [O].** A HomeCity tech is not refused by 0x4C6968 (bit 18 only skips the ResearchLimit test), but the research
start refuses it silently at 0x9E67CE (`push 12h / call 44D863h / je 9E67C5h`), before the payment. Whether its
button even shows on a unit depends on its status (bit 0 obtainable), which the home city manages for deck cards.
**Not tested in game** (it needs a WallMapu skirmish, and the shared profile may change only with no other game
open; four other games ran all day).

**What WoL writes.** The HomeCity tech in the unit's `<Tech>` rows (e.g. `HCNativeLore` on a council member), and
deletes its duplicate (`MapucheNativeLore`).

**Site.** 0x9E67CE (13 B: `push 12h / mov ecx,esi / call 44D863h / cmp al,1 / je 9E67C5h`; no branch into it; it ends
at 0x9E67DB, right before the shared payment site 0x9E67E1, which it does not touch). The hook lets a HomeCity tech
through when the researcher's proto (`[[action+10h]+5Ch]`) lists it in its command list (`[proto+E8h]`, 6-byte entries,
kind 1, count `[proto+ECh]`); else stock. ESI = the status, EDI = the player at that point ([I] from 0x9E67DE: verify
before writing).

**One status with the card [I].** The research activates the same status the card would (0x94CF27 through state 0Ah).
An active tech is not obtainable, so the card cannot be sent after it ([I]: test), and a card sent first makes the
unit's button go away. What the key must add: the card's "used" list (`[hc+260h]`, add-unique 0x444FD3 at 0x85857F)
is not updated by a research; if the deck shows the card as sendable after the research, add the card index there
when the research completes (the `started`/apply path), and check that 0x857766 / 0x857819 / 0x85798E (the home city's
HomeCity tests) refuse an active tech.
- **(WoL?)** The status the tech starts with: a deck card is obtainable only through the deck. If `HCNativeLore` is
  not in the player's deck it stays unobtainable and the council button never shows. Either WoL makes it obtainable
  (a `TechStatus obtainable` effect in `Age0Mapuche`), or the key does it for techs listed in a proto. Ask which.
- The per-tech update never auto-activates a HomeCity tech (0x68FCB7): unchanged, the research activates it.

**Tests.** WallMapu skirmish: first the stock behaviour (`HCNativeLore` on `MapucheWiseWoman` in the copy's protoy,
restored after: button shown? greyed? click?), then with the key: research it, then try the card; send the card
first, then look at the council; with and without the card in the deck.

## #72c "Let it check for the damn black town center"

**What the exe does [O].** The only readers of `CheckLandHCGatherPoint` (flag 1Eh) and `CheckWaterHCGatherPoint`
(1Fh) are in the research update (0x9E6553, 0x9E6583): every tick, a player with a home city and no land gather point
(0x4C6B9E: the stored point, else the first TC, Outpost, FortFrontier, WarHut, Blockhouse, NoblesHut, Agra fort,
Daimyo, castle, village) gets the research **cancelled with a full refund** (state 13h, 0x8D7004). The card shipment
code never reads them, so the flag is harmless on a HomeCity card. A tech without the flag whose effect is
`FreeHomeCityUnit` loses its units when there is no gather point (FUN_00857E77 bails at 0x857F3F).

**What it most likely means.** When a council member researches a **HomeCity** tech (#72b), it must check the gather
point like the council techs do, or the units of `FreeHomeCityUnit` cards vanish when the player has no Town Center.
No WallMapu TC model or texture was found that is black: `RT_Bone_wallmapu` (protoy 155578, a texture-replacing bone,
`replace_texture\wallmapu_rt_anim.xml`) is a `townstartingunit` of WallMapu and loads unit models only. **(WoL?)**
Ask Dr.Maxy what "black" means (a TC drawn black? a destroyed TC? the HC flag's drop point?).

**Design.** Data: WoL adds `<Flag>CheckLandHCGatherPoint</Flag>` (or the water one) to every HomeCity tech it puts on
a unit. No key needed. Optionally `homeCityTechsInUnits` treats a HomeCity tech researched from a unit as if it had
flag 1Eh when it has a `FreeHomeCityUnit` effect (a hook at 0x9E6553, `push 1Eh / mov ecx,ebx / call 44D863h`, 9 B),
if WoL prefers not to edit the cards.

**Test.** WallMapu skirmish: delete the TC (and every building of the fallback list), research `MapucheVillagers1`:
it is cancelled and refunded (ships back) at the next tick; rebuild a TC: it researches and the settlers arrive.

## #73 Transforms by button

**Today [O].** `uiTransformSelectedUnit("Proto")` (0x7E7193) sends a network command (type 17h) for the selection;
each unit is handled on its own (0x7D64F7): the target proto must pass the world's placement check at the unit's
position (0x50703D: in game it applied `maturing.xml`'s `obstructionatleastfromtype Mill 8` and the target's
`AllowedAge`), the target's cost is paid (else string 42A8h, "not enough resources", to the owner), the new unit is
built complete at the unit's position and the old one removed. No build-limit test was seen in 0x7D64F7. The youth is
consumed today by its single-use `Build` action; the maturing building spawns the unit (single-use `Maintain`) and
dies (Lifespan).

**So most of the request is data (WoL writes it).**
- Four commands in `protounitcommands.xml`, like the existing `TransformBowmanMaturing`:
  `uiTransformSelectedUnit("AFRICANaskariMATURING")`, `…escortMATURING`, `…revolvingcannonMATURING`,
  `…mountaingunMATURING`, with `<tech>` as needed, and `<Command>` rows on `AFRICANyouth`. The near-kraal rule then
  comes from `maturinggunpowder.xml` / `maturinghorse.xml` as for placing.
- Greek: un-comment `TransformPyrpolikon` with the right name (`PyrpolikoMaturing`, not `PyrpolikonMATURING`) on
  `FishingBoat`. [U] A water target at a boat's position: test.

**What a key adds (`transformChecks`).**
1. The button greys out with the reason: today it is always enabled and a refused transform does nothing visible
   (no message for a placement failure). The command panel builds protounitcommand buttons in FUN_0046188E (entries
   `{word id, byte kind 2}` of `[proto+E8h]`); [U] the site where a command button's enabled state and rollover are
   set was not found. The key evaluates, for the selected unit, the same check as the command: the placement check
   0x50703D (signature only partly known: `(proto, player, Vec3* pos, Vec3* orient, Vec3* obstruction, 0, 2, 0, 0, 0,
   0)`; [U] whether one of the zero arguments receives the failing rule's `errorstringid`), the cost (0x8D946A's
   test without paying) and the build limit. Interface only, so it may run every frame for the selection, but cache per
   selection and frame.
2. The build limit in the simulation: a hook in 0x7D64F7 before the payment that refuses when the player's count of
   the target proto has reached its `BuildLimit` (PyrpolikoMaturing has 5). Needed only if the WoL team relies on it.
3. **(WoL?)** Should a refused unit of a mixed selection say why (one message per command), and should the cost be
   the target's (stock) or a cost given in the command?

**Tests.** Scenario (exact positions with `Unit Create` triggers): youths near and far from a gunpowder kraal (Age II:
`tech1=` the civ's age tech), with too little gold, at the build limit, a selection of three where one is far; the
fishing boat on water and beside the shore. Already seen 2026-11-20: next to a Mill refused, far accepted; AllowedAge 2
refused at age 0.
