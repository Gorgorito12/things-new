"NEW" Levant crash (#78): the fix, tested (2026-11-23)
=====================================================

Follows wol-fixes/maps/levant-clicks-20261122.txt (the crash reproduced 4 times, and its likely cause).

Short answer
------------
There are two causes, both in how the game frees 3D models while units still use them, and both are fixed:

1. The model cache's 30 MB budget (the main one). The game unloads the model it used least recently every
   frame while its loaded models take more than 30,000,000 bytes, even when units still draw it; WoL's art is
   over that from the first minutes. Fix: our DLL's new key `modelCacheLimit 0` (no model is ever unloaded
   for the budget), or the same as a 4-byte patch of WoL's age3y.exe (below).
2. Damage templates whose "part" bones the anim file does not define, or the model lacks (a smaller one, in
   the data). When a building or tree with such a template is damaged or dies, the game writes "Invalid bone
   name ... in part declaration for model ..." and, the first time it meets that bone name, loads the model
   again while units still draw it. With the key on, one game crashed this way: a cypress tree with the oak's template, bone
   "oak a death", which the cypress models do not have. Fix: in WoL's data (files below).

With the key on and the cypress fixed: 6 games of 13.5 minutes (6 and 8 players, free for all and teams, Hard
and Expert), 0 crashes, and not one model unloaded for the budget during play (the traces). Without the key the
same clicks crashed 4 times in 7 games yesterday (2 more games without the key today did not), and today
once in 2 games with ONLY your uhc.dll (no DLL of ours at all): so it is not our test DLL. The cost is about
100 to 150 MB more memory at 10 minutes (the cache held 90 to 120 MB instead of 30).

What to do in WoL
-----------------
- Put `modelCacheLimit 0` in our DLL's cfg, or patch age3y.exe yourselves (it does the same, with no DLL):
    file offset 0x6C043:  80 C3 C9 01  ->  FF FF FF FF
    file offset 0x2E017A: 80 C3 C9 01  ->  FF FF FF FF
  Check that both offsets hold 80 C3 C9 01 first (they do in WoL's age3y.exe 0a277f14... and in the Steam
  exe). These are the two compares with the budget, 30,000,000 = 0x01C9C380; FF FF FF FF is never exceeded.
- art\War of the Triple Alliance\DLC\Other\new trees\cypress.xml: remove the three
  damagetemplate="terrain\trees\Damage\tree_oak_a.dmg" of its "death" component (the cypress models have no
  bone "oak a death", so that part never worked on them; the tree still has its death animation). The fixed file:
  wol-fixes/art-dmg-bones-20261123/art/... (same path).
- art\War of the Triple Alliance\Buildingsets\market.xml: add <definebone> for bone_debris_2Q to 2U after
  bone_debris_2P (the model has these bones; the anim file defines only up to 2P, so the game reloaded the
  West market's damaged model in every game we played with the key on). The fixed file is in the same folder.
- The other damage templates with the same fault are listed in wol-fixes/art-dmg-bones-20261123/:
  dmg-bones-wol.csv (WoL's art: 182 model and template pairs with bones the model lacks, 253 with bones the
  anim file does not define) and dmg-bones-stock.csv (the original game has 19 and 40 itself). Each one is a
  possible crash only the first time its bone name is met in a session, and only while the model is in use;
  "not defined" ones are fixed with <definebone> lines, "missing bones" ones with a template made for the
  model or no template. The list comes from aoe3-blender-tools' tools/dmg_bones.py (it reads the loose files
  and the .bar archives, and the compressed models through the game's granny2.dll).

The key
-------
  modelCacheLimit [MB] [log]
- No number, or 0: no model is ever unloaded for the budget (recommended).
- A number of megabytes (30 to 4000): models are unloaded only above it. Any limit the cache reaches can crash
  again, so use one only if memory runs short.
- log: the log says each time the cache passes a new 50 MB step.
- It rewrites the two numbers above in memory (after checking the original bytes); no hook. It works beside
  WoL's uhc.dll (our dinput8.dll; WoL's DLL does not touch these bytes) and in our UHC.dll.

Memory
------
With the key, every model a game draws stays loaded. In these sweeps (the whole map revealed and clicked,
which draws far more kinds of model than a player's camera) the cache grew to 90-120 MB in 13.5 minutes
instead of staying at 30 MB, and the process's private bytes were 1,363-1,539 MB at their peak instead of
1,267-1,328 MB (about +90 to +150 MB at 10 minutes of game time; working set 1,112-1,285 MB against
1,018-1,076 MB). WoL's exe is large-address-aware (up to 4 GB), so this is far from any limit. The cache can only
grow up to the size of all the models one game uses; a limit (modelCacheLimit 500, say) is there for a machine
that runs short of memory, at the price of the crash coming back when the cache reaches it.

#78 "NEW" Levant crash: found and fixed (tested).

The crash is not in the map script. It is the game's 3D model cache: the exe has a fixed 30 MB budget for loaded
models, and every frame it unloads the least recently used model while it is over that, even if units on the map
still use it. WoL's art keeps the cache over 30 MB from the first minutes (we counted 584 to 1,751 unloads in one
game), so sooner or later a unit draws a model that was freed under it and the game crashes inside Granny
(Windows reports age3y.exe offset 0000c07c / 0000cc7b, or granny2.dll offset 0003a02a / 0002c8cd / 0002c9a4).
Big games (6 to 8 players), clicking or scrolling over the whole map, and many civs make it more likely. It also
crashed with only your uhc.dll and none of ours, so it is the game, not a DLL.

The fix:
1. Remove the budget. Either our DLL's new key `modelCacheLimit 0`, or patch age3y.exe yourselves, 4 bytes twice:
   file offset 0x6C043: 80 C3 C9 01 -> FF FF FF FF, and file offset 0x2E017A: 80 C3 C9 01 -> FF FF FF FF
   (check both hold 80 C3 C9 01 first). Cost: about 100-150 MB more memory in a 13-minute game; WoL's exe is
   large-address-aware, so that is fine.
2. Two data errors that make the game reload a model while it is in use (same kind of crash; one game crashed
   this way with the budget removed):
   - art\War of the Triple Alliance\DLC\Other\new trees\cypress.xml uses the oak's damage template
     (terrain\trees\Damage\tree_oak_a.dmg), whose part bone "oak a death" the cypress models do not have.
     Remove the three damagetemplate="..." of its death component.
   - art\War of the Triple Alliance\Buildingsets\market.xml does not define bone_debris_2Q to 2U, which the West
     market's damaged model has: add five <definebone> lines after bone_debris_2P.
   Both fixed files are attached. We also attach a list of every other damage template with the same fault in
   WoL's art (and in the original game, which has some too); each one is a possible crash the first time its
   bone is met in a game, so they are worth fixing when you touch those files.

Tested: 6 games of 13.5 minutes on "NEW" Levant, 6 and 8 players, free for all and 4v4, Hard and Expert,
European AIs, one player clicking every unit on the revealed map: 0 crashes with the fix, and the cache never
unloaded a model during play. Before the fix the same test crashed in about half the games.
